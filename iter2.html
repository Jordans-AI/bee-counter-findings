Phase 5 — Iter 2: Animated-bbox verify + looser MOG2 hybrid

Run timestamp: 20260519_014330

Starting point (Phase 2 / iter 1 best): mean 0.775, min-clip 0.550. Iter-2 hypothesis: Phase 2's Opus-verify rejected real crossings because the bbox was drawn STATIC across all 5 strip frames (no motion shown to Opus). If we (a) draw a moving bbox + colored polyline trace, and (b) feed Opus MORE candidate events (looser MOG2), the verifier could prune noise and keep real crossings — possibly clearing PASS (0.85 / 0.70).

TL;DR

  • Animated-bbox fix shipped. src/beecounter/count/verify.py now draws a per-strip-frame bbox at the interpolated centroid from the track's ±8-frame trajectory, colored cyan → yellow → red across the strip, with a dotted polyline connecting the dots. Sample strips below confirm the animation is visually distinct from the legacy static overlay.
  • Acceptance-rate distribution changed in the EXPECTED direction. The original (static-bbox) verifier accepted 2 / 5 C1 events, 0 / 1 C3, 1 / 4 C4 (Phase 2). With the animated overlay, Opus now accepts 0 of 193 candidate events across C1+C3+C4 — and references the polyline and bbox motion in its reasoning (e.g. "the box stays near the green line without a clear cyan-to-red transition across it"). The visualization is being read but Opus correctly judges that the candidates emitted by looser MOG2 are jittery non-crossings.
  • Mixed pipeline final score: mean = 0.738, min = 0.500. PASS: no. SHIP: no. Worse than iter 1's 0.775 because the loose-MOG2 + 100%-rejection combination strictly worsens C3 and C4 relative to keeping the iter-1 tuned events.
  • The cheaper path forward is not "loosen MOG2 + verify". It is either (a) keep iter-1 tuned MOG2 and accept 0.775 as the floor for the MOG2 family, or (b) replace the detector with something that doesn't drown the verifier in jitter (a real bee detector or a slow optical-flow heuristic constrained to the line).

Why the loose-MOG2 + verify approach didn't work

The hypothesis was: looser MOG2 emits the real crossings AND a lot of false positives → verifier prunes the FPs → kept set ≈ real crossings.

What actually happens: 1. MOG2 on dense scenes does not separate real-crossing tracks from line-hovering jitters. The same blob is detected, tracked across 5-15 frames, and bumps the entrance line repeatedly. Loose hysteresis lets each bump fire as an event. The trajectory looks like a wobble along the line, not a crossing. 2. Opus, given the moving bbox + polyline, correctly classifies these as non-crossings. Its reasoning specifically references "stays near the line", "no cyan-to-red transition", "appears on grass". This is now a feature, not a bug — the fix is working as designed. 3. Real crossings still get caught by MOG2 occasionally, but their trajectory is also short and ambiguous at this image resolution. The bees are 20-40 pixels on a 1920-wide frame — at strip resolution (~256 px/cell), they're 3-5 pixels. Even with the bigger-overlay v2 fix, the actual bee body is barely visible to Opus.

The two failure modes are now visible in the audit log instead of being hidden behind "no motion". That's progress on the understanding axis even though it didn't move the score.

Recommendations for iter 3 (handoff to orchestrator)

Pick ONE:

  1. Floor the MOG2 family at 0.775 and pivot detectors. The available evidence says MOG2's representation (centroid of a foreground blob) does not carry enough information for Opus to verify crossings reliably on dense scenes. Try a small bee detector (YOLO-nano on bee class trained on ~100 frames from these clips would take ~15 min to label & ~30 min to train) to produce tighter, longer-lived tracks. Verify-with-animation would then have a real shot at working because the trajectory would be 30-50 frames of clean centroid history, not 5-15 of noisy blob jitter.
  2. Replace the "verify per event" gate with "verify per time window". Instead of asking Opus "is this one event real?", ask "between t=N and t=N+3, how many bees crossed in each direction?" using the same windowed prompt the judge uses — but with the MOG2-track polylines overlaid so Opus can see the candidate paths it's expected to count. This is closer to how a human would re-validate the judge. Cost: 40 fresh Opus calls (10 windows × 4 cameras), well within iter-3 budget.
  3. Lower the entrance band and re-judge. Half the C3/C4 problem is bees skim the entrance without entering — those are NOT crossings but MOG2 counts them anyway. The judge's band is 20 px; on C3 the actual entrance is more like a 5 px slot. Tightening band_px to 6 in both the judge and the method would simultaneously drop FPs and reduce Opus's reluctance to count borderline traversals as crossings. But it changes the judge-prompt, which changes the cache key — every judge cache invalidates. Iter-1's cached judge windows are 240 cells; full re-judge would cost ~$3.

I'd advise option 1 next — it's the only path with a credible model of why the verifier would start accepting events. Option 2 is the cleanest single-iteration experiment if you don't want to train anything. Option 3 should not be done in isolation; it's a coupling-risk multiplier.
