Why sub-step 2b did not help

Opus rejected most candidate crossings (8 of 10 raw events across C1/C3/C4 marked is_real_crossing=False, confidence 0.20-0.30). Spot-checks of the audit JSON show the model's consistent objection is that the cyan bounding box overlay is drawn at the event frame's position on ALL 5 strip frames — so it appears static in the strip image, which makes Opus reluctant to call it a 'crossing in motion'. The two events that survived on C1 were both api-error: OverloadedError fallbacks (we default to keep on API failure), not true positive verifications.

Because the tuner had already pushed each clip onto a tight (low-event, high-precision) operating point, dropping any further events overshoots toward 0/0, which scores worse against a judge that reports non-zero crossings (C3 4/6, C4 2/5). On those clips the verified score dropped (C3 0.55→0.50, C4 0.75→0.60) and we honored the brief's revert clause.

Potential improvements (out of scope for this run, recorded for Phase 3): - Re-render the strip so the bbox tracks the actual track centroid per-frame, not the static event-frame location. This would let Opus see the bee's motion. - Drop the bbox entirely and present just the 5 raw frames + entrance line; ask Opus to confirm the direction matches the visible bee motion. - Run verification with a looser tuned config (more events, more FP) so verification has actual work to do; the current tuned config already filters aggressively.
