Bee In/Out Counter — Specification

Problem

Given video footage from a camera placed at a bee-hive entrance, output a reliable count of bees entering the hive and bees exiting the hive over the duration of each video.

Quality (accuracy on entrance/exit counts) is the only first-order metric. Throughput, runtime, model size, and code elegance are all secondary.

Data

Four 30s @ 30fps 1080p H.264 clips, one per camera, at data/raw/videos/<camera>/. Camera names are Hebrew; treat them as opaque IDs:

ID Folder Notable conditions
C1 מצלמה1_אוכמניות Low side-angle of landing board, partial grass occlusion, ~10–20 bees
C2 מצלמה2_בהג_ט Cleaner side view, sparse flying bees against sky, ~5–10 bees
C3 מצלמה3_בדרךלקיווי Angled top view of densely populated landing board, crowd at entrance
C4 מצלמה4_דובדבן Low side-angle, heavy grass occlusion, mixed crawling + flying

There is no ground truth, no validation set, no test set. The four clips are the whole dataset. We must bootstrap evaluation from Claude vision (see §Validation).

Definitions

  • Entrance line: a 2D segment per camera marking the lip of the hive opening, with a consistent "inside" normal direction (toward the box interior).
  • Bee event: a track whose centroid crosses the entrance line.
  • "in" = the segment of the track crossing from outside to inside.
  • "out" = the segment of the track crossing from inside to outside.
  • A track may have multiple events (hovers, retreats); each line crossing counts.
  • Bee here includes both flying and crawling individuals. Wasps/flies are out of scope but should not pollute the count if avoidable.

Outputs (per video)

  1. events.jsonl — one record per crossing event: {video_id, frame_idx, t_sec, track_id, direction, bbox, confidence}
  2. counts.json — totals: {video_id, total_in, total_out, net_in_minus_out, duration_s}
  3. annotated.mp4 — overlay rendering: boxes, track IDs, entrance line, running IN: x | OUT: y counter.
  4. report.md — per-video summary with method, parameters, judge-agreement score, failure cases identified by the viewer.

Architecture (target)

video → frame iterator → detector(s) → tracker → entrance-line counter → events → counts
                                                       │
                                                       └→ annotated.mp4 + viewer cache

Plug-in interfaces so multiple detector and tracker backends can be A/B tested behind the same counting and validation harness.

Validation protocol (Claude-as-judge)

Without GT we bootstrap a pseudo-ground-truth signal:

  1. Judge protocol — single-frame counts. Sample N stratified frames per video (uniform + high-motion). Ask Claude Opus 4.7 vision to count bees visible and to count bees within a small band around the entrance line. Record per-frame counts.
  2. Judge protocol — short-clip event counts. For each video, slice into 3–5 second sub-clips, send a short MP4 / strip of frames to Claude Opus 4.7 and ask for (in, out) for that window. Aggregate to the per-video totals.
  3. Method scoring. A method's score on a clip is 1 - |method_in - judge_in| / max(judge_in, 1) (and likewise for out); the overall score is the mean across the four clips. ≥ 0.85 mean agreement is the bar for "good"; ≥ 0.92 is the bar for "ship".
  4. Cross-method agreement is an independent signal: if three independent detectors agree on a count within ±1, that increases confidence even before judging.
  5. Cache every judge call (request hash → response) in data/judge_cache/ so repeated runs don't re-spend API.

The judge is fallible. Treat judge-vs-method disagreements as cases to inspect via the viewer, not as automatic method failures. When the viewer reveals the judge was wrong, record the example and adjust the prompt.

Candidate technologies (Phase 1 — bake-off)

Implement each behind a uniform Detector interface, run on all 4 clips, score by §4.

A. Detection + tracking (off-the-shelf) - A1. YOLO11x (ultralytics) + ByteTrack - A2. YOLO11x + SAHI (sliced inference for small bees) + ByteTrack - A3. RT-DETR-X + BoT-SORT

B. Foundation / zero-shot - B1. GroundingDINO ("bee . honey bee . insect") + ByteTrack - B2. OWLv2 ("a honeybee") + ByteTrack - B3. SAM2 video propagation seeded from B1 boxes on key frames

C. Classical CV - C1. MOG2 background subtraction + connected-component blobs + Hungarian assignment - C2. Optical-flow (Farneback / RAFT) on entrance ROI + flow-direction integration

D. Hybrid (only after A/B/C measurements exist) - D1. Background-subtraction ROIs fed to the strongest detector - D2. Ensemble vote across the top 3 methods with weighted NMS

Phase-1 winner = highest mean score across the 4 clips, with consistency (lowest stdev).

Phase 2 — improve the winner

  • Tune per-camera: entrance line, ROI mask, confidence threshold, tracker params.
  • If the Phase-1 winner clears ≥ 0.85 mean judge-agreement → skip fine-tuning, polish the winner.
  • If it does NOT clear 0.85 → use the judge to pseudo-label ~200–500 frames (boxes via Claude Opus vision asked to output JSON coordinates, sanity-filtered by IoU with the zero-shot detector), then fine-tune YOLO11s on those crops. Re-score.
  • Try the ensemble (D2) on the winner + the next two strongest methods. Ship the ensemble only if it strictly improves agreement on every clip.

Phase 3 — viewer (debugging tool, dual-use)

A small local FastAPI app (uv run bee viewer) that: - Lists runs and clips. - Plays the annotated video with synchronized event/track overlays. - Lets the user (and the agent itself) scrub frame-by-frame, jump to crossing events, toggle detector overlays. - Renders the per-frame judge counts vs the method counts as a time series. - Exports failure cases (frame range + reason) into failures.jsonl, which the agent can read to drive the next iteration.

The viewer is built early — by end of Phase 1 — so it doubles as the agent's debug loop.

Non-goals

  • Real-time / streaming inference.
  • Bee species classification.
  • Tracking individual bees across multiple videos.
  • A polished user-facing UI (the viewer is a debugging tool).

Deliverables (end of overnight run)

  1. results/runs/<timestamp>/ containing per-method counts and judge scores.
  2. bakeoff.md — Phase 1 comparison table with screenshots.
  3. final.md — winning pipeline, per-video counts, agreement scores, known failure modes, recommended next steps.
  4. The viewer, runnable via uv run bee viewer.
  5. A reproducible make demo (or bee run --all) that regenerates §1–4 from raw video.
