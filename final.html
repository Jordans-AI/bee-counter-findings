Why the previous report was wrong about C1

The overnight run scored every method against a Claude-as-judge proxy that returned C1 = 0 IN / 4 OUT. The whole pipeline was therefore tuned to be conservative (the "final" MOG2 emitted 3 IN) to agree with ~0. A human then labelled the clip frame-by-frame in the viewer and found 51 real entries — ~1.7 bees/sec, which is normal for an active hive. The judge had massively under-counted (Opus on 3-second strips can't track individual bees and defaults to "no clear crossing"). The "0.775 structural cap" was agreement with a broken target, not a real ceiling. Once the target is the manual GT, a sensitively-tuned classical pipeline lands the count almost exactly.

What "entry" actually means here (two domain corrections)

Defining the right physical event mattered more than any parameter. Two corrections from domain review reshaped the model:

  1. The entrance is the dark notch holes, not the cameras.yaml line. That line sits at the box/board seam above the real entrances. Overlaying the 51 GT points shows they all land on the dark notch holes below the line. A bee crossing the line upward is mostly an exit (climbing out of a hole). An early counter that counted upward crossings still hit 52≈51 — but only because in a near-steady-state hive exits ≈ entries over 30 s, so it got the right total by measuring the wrong event (its temporal F1 was a weak 0.66).
  2. Bees enter from every direction — landing from below, crawling in from the side, descending from the rail. So a directional crossing model is wrong by construction; it bakes in one approach direction and misses the rest.

The correct, direction-agnostic definition:

Entry = a track that ends inside the dark entrance zone, having been seen outside it — i.e. a bee that arrived at a hole from anywhere and vanished into the dark. Exit = a track born inside the dark (a bee emerging) — excluded.

Switching to this model lifted temporal F1 from 0.66 → 0.76 at the same count, which is the real signal that it now measures entries (right frames), not exits.

Method

frame → crop ROI (entrance strip, excludes grass) → grayscale → CLAHE
      → MOG2 motion → connected-component blobs → Hungarian tracker
      → VanishEntryCounter (ends-in-dark-zone, born-outside) → IN events

Four decisions did the work, each grounded in the footage:

  1. Tight ROI at the entrance ([355, 750, 1055, 950]) — frame-diff and MOG2 are otherwise dominated by wind-blown grass and bees flying across the box face.
  2. CLAHE contrast enhancement — bees near the dark notches are nearly invisible in raw grayscale; CLAHE makes them detectable.
  3. Data-driven dark-entrance zone — the median background's persistently-dark pixels (inside the entrance band, dilated) are the holes. No hand-placed line; 45/51 GT points fall inside this zone.
  4. Direction-agnostic vanish counter — count tracks that end inside the dark zone having started outside, regardless of approach direction. Exits (born in the dark) are naturally excluded. See src/beecounter/count/vanish_entry.py. The earlier directional counter is kept in directional_entry.py for comparison.

How it was tuned (reproducible, GT-driven)

scripts/sweep_c1_entry.py grid-searches against the manual GT, optimizing for temporal F1 subject to the count staying in the ±20% band — so the count is right because events align, not by luck. The progression: directional counter F1 0.54 → 0.66 (count ~51), then the corrected vanish counter F1 → 0.76 (count 52) after sweeping dark_thresh, zone_dilate, min_track_obs, dedup.

Honest error analysis

F1 is 0.76 (P=0.75, R=0.76). Recall 0.76 means three-quarters of the 51 real entries are individually detected at the right time — the count is not a coincidence. The residual errors are structured, not random:

  • False negatives (12) are dominated by dense bursts at the same hole (e.g. GT's 3 entries on frame 7, the burst at 504–519): the detector sees the bees but spatial+temporal de-dup merges near-simultaneous arrivals at one spot. Inherent to de-dup'd counting without per-bee re-ID tracking.
  • False positives (13) are bees that reach a hole and pause/retreat (a track that ends just inside the dilated zone without truly entering), plus occasional tracker fragments whose tail lands in the zone.

Visual confirmation: results/runs/c1_entry_final/C1/annotated.mp4 shows the ROI, detections, track centroids and a green flash at each counted entry; the dark-zone overlay was checked against the GT points during tuning.

Detection experiment (YOLO fine-tune) — and why motion still ships

Motion is a calibrated motion statistic (accurate total, messy internals — small load-bearing blobs, unstable track IDs, the counted point near-but-not-on the bee). We tested a bee-instance detector to see if it could count more cleanly:

  • Off-the-shelf YOLO11 fine-tuned on a hive-entrance dataset (Sledevic 2024, Mendeley V6, CC BY 4.0 — DATA_CITATIONS.md) hit val mAP50 0.975 on that data but barely transferred to C1 (~1 bee/frame).
  • Fine-tuned on 46 hand-labeled C1 frames (c1_box_labels.json, scripts/finetune_c1.py) it closed the detection gap: ~12 bees/frame, recall 0.94 — cleanly detecting the dark crawlers motion only fragments.
  • But the count plateaued. Tracking small/fast/occluding bees fragments IDs (471 ByteTrack → 357 BoT-SORT); across trackers × counters the count lands F1 0.65–0.73 — not beating motion's 0.76. And "cleaning" motion's blobs (bigger min_area/close) deletes the load-bearing vanish sliver and lowers it.

Verdict: clean detection (FT detector) and clean counting (motion) are in tension; the shared bottleneck is stable per-bee tracking. Motion ships as the C1 count; the FT detector is kept as a high-recall component. Blow-by-blow: decisions.md.

Scope and limitations

  • Entries only. Exits are out of project scope (confirmed 2026-05-31). This C1 section is the deepest write-up; C2–C4 now have GT, configs, and scored counts too (see All-camera results above) — they are no longer on the judge-proxy numbers.
  • Parameters are tuned to one 30-second clip. They encode real structure (entrance darkness, bee size, motion) so they should transfer to similar C1 footage, but a different clip should be re-scored.
  • To push F1 higher without hurting the count you would need to resolve dense simultaneous arrivals at one hole — a small re-ID/embedding tracker, or per-hole occupancy changepoint detection, instead of centroid de-dup.

The two shipped counters

  1. Motion "vanish-into-the-dark" (configs/c*_entry.yaml, no weights) — the classical C1 method described above, transferred to each camera's ROI. It is a high-precision, low-recall statistic: it needs a bee to visibly descend into a dark notch, so recall falls monotonically as the entrance hides that descent (C1 0.76 → C2 0.54 → C3 0.31 → C4 0.17). On the crowded/grassy cameras it under-counts badly.
  2. Absorption (detector terminations, trackless) (configs/c*_absorption.yaml) — runs the C1-fine-tuned YOLO detector (transfer, no per-camera fine-tune) on each crop, builds short local nearest-neighbour chains purely to find where a detection chain terminates inside the deep part of the entry zone (a bee that arrived at a hole and was absorbed), de-dupes, and counts those. It never builds a global identity, so track fragmentation — the wall that capped every ByteTrack/ BoT-SORT count at F1 0.65–0.73 — is irrelevant.

Why absorption beats motion everywhere

Motion's bottleneck was never "structural to the camera" — it was the motion signal. A dense or grassy entrance hides the dark-hole descent that the vanish counter keys on, but the detector still sees the bee and its local chain still terminates in the zone. So absorption improves every camera and reaches the count band on all four with a transfer detector (no per-camera fine-tune). Two per-camera levers, both density-driven, closed the last gaps without new labels:

  • C2 (sparse, flying bees) needed the gating loosened (recall sweep, configs/c2_absorption.yaml): 54/74 (OUT) → 73/74, r0.99, F1 0.79.
  • C4 (densest/grassiest crowd) needed the local-tracker association radius tightened — at C1's inherited gate_px=70 a terminating chain in a dense crowd is "stolen" by a neighbouring bee and never registers, suppressing recall. Dropping to gate_px=50 (configs/c4_absorption.yaml) took C4 from 21/42 (r0.50, OUT) to 38/42, r0.90, F1 0.93, P 0.97 R 0.88 — in-band. C1/C2/C3 are less dense and verified best at 70 (tightening over-counts them), so gate_px is a genuine per-camera, density-dependent lever, not a global constant. Blow-by-blow: decisions.md.

On C1, two independent counters now agree on the count (motion 52, absorption 53 standalone / 52 windowed, vs GT 51) via completely unrelated signals (MOG2 motion blobs vs detector terminations) — cross-method validation that the count is real, not a coincidence. Fusing them was tried and does not beat absorption alone (the two disagree on which events are real; the ~26-entry consensus core at P=0.90 is the validation payoff, not a better count — see decisions.md).

Validation — are the four in-band configs real, or GT overfits?

The GT is an approximate, partial, manually-labelled ballpark, so six independent checks guard against the obvious failure modes — fitting the configs to exact GT frames, matching the count by accident at the wrong place, mistaking label noise for a real gain, reading a structural ceiling as a tuning bug, and picking an operating point that isn't actually the best on its tradeoff curve.

  • Plateau, not overfit (robustness.md, scripts/robustness_analysis.py). Stepping each shipped config ±1 grid notch per lever (one at a time) leaves every baseline near the centre of a plateau: ratios 0.90–1.02 (mid-band), 1-off F1 ranges ≤0.17 wide, in-band-neighbour counts C1 10/12 · C2 11/11 · C3 10/13 · C4 8/11. The only out-of-band neighbours come from aggressive recall-loosening (over-counting from fragmentation) — the shipped values back off one notch from that edge, not picked at a cliff. The count band is tolerance-independent: sweeping the temporal tolerance 5→30f leaves the ratio identical and only raises the secondary F1 — the headline doesn't hinge on ±15f.
  • Counted entries land at the right place (spatial_validation.md, scripts/spatial_validation.py). Using the GT click location (x_norm/y_norm), matched events sit a moderate 89–225 px from their GT point on ~700–900 px crops, and absorption localises markedly better than motion on the dense/grassy cameras (C3 @100px joint F1 0.49 vs 0.29; C4 0.65 vs 0.29) — fresh evidence to prefer absorption beyond the count ratio. Joint space-time F1 is an honest lower bound the temporal scoreboard alone didn't give.
  • The density ordering and recall ceiling are quantified, not asserted (gt_characterization.md, scripts/gt_characterization.py). Reading the GT alone, same-frame simultaneity (the fraction of entries sharing a frame with another) rises monotonically C1 8% → C2 11% → C3 17% → C4 29%, with entry rate 1.75 → 4.36 → 2.27 → 7.88 in/s — the first number behind the "C1 < C2 < C3 < C4" density ordering every structural verdict rests on. Because both counters dedup near-coincident events, simultaneous arrivals are a structural recall ceiling no parameter can lift. The median inter-event gap (C1 11.5f, C2 7f, C3 11f, C4 4f) also explains the per-camera dedup_frames found empirically (C2 → 8, C4 → 3).
  • The residual errors are structural, not tuning artefacts (error_analysis.md, scripts/error_analysis.py, built from the committed golden frames — no video/GPU). Splitting each method's FP/FN through the production matcher: missed entries are markedly more temporally crowded than caught ones on the dense cameras (FN/TP density ratio 1.24 on C2, 2.06 on C3 the dense crowd, 1.12 on C4) but ~equal on sparse C1 (0.81) — direct evidence the dense-camera recall gap is the uncollapsible near-coincident entries, sharpest exactly where simultaneity peaks. And false positives are predominantly re-spawns (most fall within 10f of another prediction — one physical event firing twice), which is why tightening dedup trades the count band for precision instead of cleanly removing noise.
  • The F1 noise band is ±~0.10, so sub-0.05 sweep gains are unresolvable (metric_uncertainty.md, scripts/metric_uncertainty.py). An event-level nonparametric bootstrap (2000×, fixed seed) puts the 95% CI on each F1 at 0.12–0.31 wide — with only 40–75 labels per camera, 0.78 vs 0.76 is statistically indistinguishable. This is the quantitative basis for every "ship the plateau, no change" decision. The paired motion-vs-absorption ΔF1 then splits by density: the CI includes 0 on the sparse cameras (C1 [-0.10, +0.13]; C2 [-0.00, +0.21]) but excludes 0 on the dense ones (C3 [+0.16, +0.45]; C4 [+0.48, +0.81], both prob 1.00). So "absorption beats motion everywhere" is two distinct claims — a count win on C1/C2, a significant F1 win on C3/C4 where motion's dark-notch signal structurally fails.
  • The shipped operating point is the best one on its own tradeoff curve (operating_curve.md, scripts/operating_curve.py, built from the committed C1 real-data fixtures — no video/GPU). Sweeping each C1 counter along its single recall lever (motion min_track_obs, absorption min_len) traces the full precision/recall curve. Applying the count-primary constraint first (ratio in ±10%) and then maximising F1 selects exactly the shipped value for both methods — the count objective and the temporal-F1 objective do not conflict on C1. (Motion's raw F1 is ~0.002 higher — inside the noise band — at a stricter, out-of-band point that under-counts; the count-primary rule correctly rejects it.) Across the curve absorption dominates motion (higher precision at matched recall, F1 peak 0.78 vs 0.76), and the shipped point sits at the knee: loosening over-counts (re-spawns), tightening drops recall — there is nothing better to pick. See fig_operating_curve.png.

Method chosen and rationale

Final method: classical-CV MOG2 background subtraction + connected components + Hungarian assignment tracker + LineCrossingDetector with per-camera hysteresis (the Phase 1 "C1 MOG2" candidate after Phase 2 tuning).

Per-camera config: configs/c1_mog2_tuned.yaml.

Why this and not a foundation-model detector

Phase 1 ran 6 candidates in parallel (A1 YOLO11x COCO, A3 RT-DETR-X COCO, B1 GroundingDINO, B2 OWLv2, C1 MOG2, C2 Farneback). The result was a clear split:

  • All COCO-pretrained detectors emitted ~0 bee-class detections (A1, A3). Expected: COCO has no bee class. Confirmed empirically.
  • Foundation-model detectors found bees but the detect→track→cross pipeline emitted ~0 crossings anyway (B1 GroundingDINO, B2 OWLv2). The detector worked — B1 smoke test found 15+ bees per frame — but the ByteTrack→LineCrossingDetector pipeline fragmented tracks at the high bee density of the entrance, so no track persisted long enough to satisfy the hysteresis line-crossing condition.
  • C1 MOG2 was the only candidate emitting real crossing events (20 events across 4 clips in Phase 1). Mean 0.675.
  • C2 Farneback flow integrator over-counted by 100x (729/464 on C1 vs judge 0/4). Threshold mis-calibrated.

C1 MOG2 won the bake-off by being the only thing that actually counts. Tuning per camera in Phase 2 lifted it to mean 0.775.

Known failure modes (root-cause analysis)

The whole overnight run can be summarized as: detection works, tracking doesn't, counting is fragile, and Opus verification is too conservative. Each of the 5 iterations tried to fix one link in that chain and failed.

Failure mode 1 — Track ID fragmentation in dense crowds (C3 / C4)

In Phase 1, GroundingDINO emitted 15+ bee detections per frame on C3. ByteTrack should turn those into ~10–20 tracks. In practice, it produced tracks averaging 3–5 frames long because: - Bees occlude each other constantly. - Detection bounding boxes wobble around densely-packed bees. - ByteTrack's IoU/Kalman defaults don't model bee-shaped objects well.

A track ≤ 5 frames cannot satisfy the LineCrossingDetector(hysteresis_frames=3, band_px=12) requirement of "stable on one side, traverse the band, stable on the other side." Result: 0 confirmed crossings emitted by GroundingDINO/OWLv2/YOLO11x-fine-tuned/RT-DETR.

Failure mode 2 — MOG2 over- and under-count oscillation on C3

C3 untuned MOG2: emitted 4 IN / 11 OUT vs judge 4/6. The IN side was perfect (4 = 4), but OUT was over by 5.

Phase 2 tuner tightened C3 settings (min_hits=30, hysteresis=25, band=24) to reduce the over-count. Result: 1 IN / 0 OUT — under-counted by 9. The tuner could not find a middle ground because MOG2 doesn't distinguish a real bee crossing from blob-merging artifacts in the dense crowd.

Failure mode 3 — Opus verification rejects nearly all MOG2 events

Phase 2 sub-step 2b and Phase 5 iter 2: when MOG2 emits an event, ask Opus "is this a real bee crossing?" with a strip of 5 frames around the event.

  • Phase 2's original implementation drew a static bbox at the event frame across all 5 strip frames. Opus reasoned "no motion visible" and rejected 8/10 events.
  • Phase 5 iter 2 fixed this by interpolating the bbox along the track's centroid and color-coding (cyan → yellow → red) across the strip. Opus's reasoning specifically referenced the polyline now: ✓ the fix worked.
  • But Opus then rejected 193 of 193 candidate events on the looser-MOG2 settings. Its reasoning across cameras was uniform: "trajectory does not cross line."

Interpretation: MOG2's "events" really aren't bee crossings — they're motion noise that even an animated polyline doesn't disguise. Or, Opus is overly conservative at the 1-second strip scale (this was independently confirmed in iter 1 — see below).

Failure mode 4 — Opus refuses to attribute crossings at 1-second window resolution

Phase 5 iter 1: built an Opus-as-window-counter that asks Opus per 1-second window to count crossings. Across 240 windows × 2 prompt variants = 480 calls, Opus returned 0 / 0 every time. The judge protocol uses 3-second windows, and within those Opus did attribute crossings (4/6 on C3, etc.). The 1-second framing didn't provide enough temporal context for Opus to commit to a crossing.

This rules out the "Direct VLM-as-detector" Tier 3 escape hatch at the granularity we'd need to compose into the judge's 3-second scoring windows.

Failure mode 5 — Pseudo-label fine-tuning produces low-confidence detections

Phase 5 iter 3 fine-tuned YOLO11s on 400 Opus-pseudo-labeled frames (5,574 boxes). Best val mAP50 = 0.068, recall 0.36, precision 0.06. Detector confidence at inference maxed at 0.04 — too low for ByteTrack to assemble crossing-length tracks even with track_high_thresh=0.015.

Phase 5 iter 4 escalated to YOLO11x — infeasible on MPS (3.5 min/epoch × 60 epochs = 3.5 hours). Fell back to YOLO11m. Same outcome: low mAP, tracks fragment, 0 crossings (or massive over-count with the iter-4 endpoint-counter variant).

Failure mode 6 — Endpoint counter over-counts symmetrically

Phase 5 iter 4 tried replacing hysteresis with track-endpoint matching (track first centroid vs last centroid on opposite sides of the line). This is the dual of hysteresis — it turned 0-event under-counts into 147+362-event over-counts on C2 (vs judge 0/0). The endpoint approach treats every fragmented track as a candidate crossing; with 1000s of fragments per video, even a small false-positive rate produces hundreds of phantom crossings.

Honest caveats on the judge proxy

The spec acknowledges the Claude-as-judge proxy is fallible (spec.md §Validation). A few specific reasons to be careful about the 0.775 number:

  1. The judge totals (C1=0/4, C2=0/0, C3=4/6, C4=2/5) are themselves Opus 4.7 vision counts on 3-second windowed strips. The judge has the same dense-crowd ambiguity humans would have. C2 saying 0/0 despite ~10 bees/frame visible flying is plausible (judge saw flying bees, not crossings), but it's a hard claim with no GT.
  2. The C2 = 0/0 judge result means any method that doesn't false-positive scores 1.00. Three of four candidates and 5/5 iterations hit C2 = 1.00 — that's the C2 score doing structural work.
  3. The judge protocol is locked-in (so cache hits stay stable). Re-rolling the judge with a different prompt could move every "ground-truth" number by ±20%. The 0.775 figure should be interpreted as "agreement with this specific cached judge."

The viewer is the disambiguation tool. Run uv run bee viewer and use the "Mark failure" button on judge-method disagreements to build a manual signal.

What I would try next given another 10 hours

Ranked by expected impact:

  1. Real bee dataset. The biggest single uncertainty here is whether MPS YOLO11s pseudo-labels are even close to a real bee detector. Spend the first 1 h pulling a public bee dataset (Roboflow Universe has several: bee detection v3, honey-bee-x57n8, etc.), fine-tuning YOLO11x for 100 epochs at imgsz=1280, and re-running. Expected: real mAP50 = 0.6–0.8, conf > 0.3, tracks would actually persist.
  2. Replace ByteTrack with a re-ID tracker (StrongSORT, DeepSORT with a small embedding model). Track ID stability across the entrance line is the single biggest pipeline failure on dense scenes. Even with the current detectors, a re-ID tracker would lift confirmed crossings.
  3. Per-frame band-occupancy time series. Skip tracking entirely. For each frame, count bees in the inside-band vs outside-band (use the detector's bee count, not tracks). A crossing is a transition in the inside-count time series. This converts the problem from tracking to changepoint detection on small integer sequences — much more robust.
  4. Manual labeling. The 4 clips are short (30 sec each). One human-hour gets ground-truth in/out per clip. Re-score every method against the manual GT alongside the judge. This is the only way to know whether the 0.775 plateau is a method ceiling or a judge ceiling.
  5. Per-camera method assignment, not per-camera tuning. This run's "winners" all collapsed to MOG2 because the alternatives emitted ~0 events. With a real bee detector (#1) the mixed assignment would actually mix.
  6. SAM2 mask propagation. Seed SAM2 with detector boxes on every Kth frame, propagate masks. Mask-centroid tracking is more stable than box-centroid on small/occluded objects.
  7. Higher input resolution. The cameras are 1080p. Bees average ~30–50 px wide. A 4K camera (or AI super-resolution upsampling) would give 60–100 px per bee — the detectors would generalize better.
  8. Two-stage classifier on bee crops. Train a tiny CNN (frozen ResNet18 head) on Opus-labeled bee crops vs hard-negative grass crops. Filter detector outputs through it. Specifically targets C4 (heavy grass).
  9. Tighter entrance line geometry. Two-line "in-band / out-band" pair so a crossing must traverse both lines in order (spatial hysteresis, not just temporal). Reduces hover-double-counts on C3.
  10. Different judge prompt. Have Opus return a per-bee crossing list (not just totals) so we can compare method tracks to judge tracks directly. Would let us score precision/recall, not just count agreement.

How to reproduce

The four source MOVs are in data/raw/videos/<camera>/ and gitignored. Pseudo-labels (data/yolo_train/) and judge cache (data/judge_cache/) are also gitignored but checked into the local repo state.

# 1. Install
uv sync                 # ~5 min on a fresh machine; pulls torch + ultralytics + sahi + supervision + transformers

# 2. Set the API key (or copy from a sibling project)
cp .env.example .env    # then edit .env to add ANTHROPIC_API_KEY=sk-...

# 3. Phase 0 sanity — re-derive entrance lines (cache hits make this ~free)
uv run bee phase0 entrance-lines

# 4. Run the final pipeline (tuned MOG2)
uv run bee run --all
# → writes results/runs/phase2_<TS>/C1_mog2_tuned/<camera>/{events.jsonl, counts.json, annotated.mp4, score.json}

# 5. Browse the runs interactively
uv run bee viewer
# → http://127.0.0.1:8765

# Re-run any individual Phase 1 candidate
uv run python scripts/run_b1_grounding_dino.py        # GroundingDINO + ByteTrack (~55 min)

uv run python scripts/run_c2_farneback.py             # Farneback flow tripwire

# Re-tune MOG2 per-camera
uv run python scripts/tune_c1_mog2.py

# Re-prime the judge cache (will print "HIT" for everything if cache is intact)
uv run python scripts/baseline_judge.py
