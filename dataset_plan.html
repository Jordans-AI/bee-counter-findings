Full-dataset bee-entry counting — plan & measurable goals

Takeover task (2026-06-20): a much larger set of hive-entrance videos arrived from Google Drive. The repo previously had only one 30 s clip per camera; the new dataset is 704 videos across the same four physical cameras. This plan states the verifiable goals and how each is checked. Method choices follow the shipped pipeline (see final.md / decisions.md); this task scales it to the whole recording, it does not re-invent the counter.

What arrived (Phase 1, done)

  • 23-part Drive ZIP (45 GB), extracted with ditto into data/raw/incoming/ (gitignored). Contents: 704 .MOV, 2011 .JPG stills, 3 Thumbs.db.
  • Manifest: data/dataset_manifest.{csv,json} (scripts/build_manifest.py), ffprobe of every video, 0 probe failures.
  • All clips: 2026-04-30, ~12:00–16:40 UTC, 1920×1080 @ 30 fps, ~30 s (900 frames; 2 short 4 s clips). Total footage 5.85 h.
  • Camera folders 1..4 → C1..C4 (the long-standing מצלמה1..4 convention). Counts: C1 349, C2 303, C3 23, C4 29. Stills are not part of the video count pipeline.

Method (transfers unchanged — the cameras are static)

The shipped absorption counter: C1-fine-tuned YOLO detector (transfer, preset bright, conf 0.1) on each camera's microscope crop → short greedy local chains → count chains that terminate deep inside the entry-zone polygon (a bee absorbed into a dark hole). Per-camera crop (microscope.yaml), zone (entry_zones.yaml), and gating (c{n}_absorption.yaml) are reused verbatim. scripts/dataset_pipeline.py.

Non-goals (per spec + CLAUDE.md)

Exits (entries only), real-time inference, species ID, re-ID across clips, per-camera re-fine-tuning (the transfer detector already lands all four sample clips in the ±10% band; GT here is an approximate ballpark — no F1 overfitting).

Run mechanics

  • Detection is GPU-bound → serial on MPS (PYTORCH_ENABLE_MPS_FALLBACK=1), ~16 s/clip, ~3.2 h for 704. Counting is pure-Python and folded into the same pass.
  • Idempotent + resumable: finished clips are skipped, so the run survives interruption.
  • No videos/weights committed — only manifest, timeline, configs, code, reports, plots.

Phase 7 — camera-geometry correction (2026-06-21, IN PROGRESS)

Manual quality-gate review (Phase 3 assumption was over-optimistic) found the cameras move over the session and the edges hold non-recording events. Full write-up + lessons: camera_geometry.md. Exclusions: configs/valid_windows.yaml.

Summary: C1 small settle (no re-detect, drop 1 install clip); C2 one ~157px jump at 12:36 + grass + final fall (crop+zone re-drawn, drop install/stray/segment-A/fall → valid window IMAG0056–1208); C3 stable (drop 1 removal clip); C4 crop+zone re-drawn (keep all).

Re-run plan — SUBSET only (counts are NOT yet corrected)

  1. Visual sanity sign-off by the user on the new C2/C4 geometry (via the clip debugger, which already shows the new crop+zone) — gate before any re-run.
  2. Re-detect C2 valid window (IMAG0056–1208, ~289 clips) + C4 (29 clips) on the new crops; recount. C1/C3 are not re-detected.
  3. Apply valid_windows.yaml at aggregation (drop excluded clips for all cameras).
  4. Regenerate stats / timeline / plots / insights (Phase 6 scripts) from corrected counts; report before/after impact.

Process lesson for future runs

Add a geometry quality-gate (framing-stability + edge-clip check) before the big count, and prefer re-running on small subsets (a camera, a window) over full re-runs. The counting pipeline is idempotent/resumable, so per-camera re-detection (--camera, --redetect) is the unit of re-work.
