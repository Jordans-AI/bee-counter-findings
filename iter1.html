Phase 5 — Iter 1: Opus-as-window-counter + per-camera best method

Run timestamp: 20260519_011549

Starting point (Phase 2 best): mean 0.775, min-clip 0.550.

Goal of iter 1: build a second, independent method (Tier 3 from OVERNIGHT_PROMPT.md, "Direct VLM-as-detector"), combine it per-camera with the tuned MOG2, and see if a mixed pipeline clears PASS (≥ 0.85 mean / ≥ 0.70 min-clip) or SHIP (≥ 0.92 / ≥ 0.85).

TL;DR

  • New method: Opus window counter (src/beecounter/count/opus_window_counter.py). 1-second windows, 6 frames each, deliberately different prompt + overlay from the judge's. 30 calls × 4 cameras × 2 prompts = 240 fresh Opus calls.
  • Opus method scored 0/0 on every single window on every camera. Model refused to attribute any crossing under both the standard and the strict prompts.
  • Mixed per-camera assignment picked tuned MOG2 on all 4 cameras, because Opus-window never strictly beat MOG2 (it tied on C1 and C2 — tie-breaker favours the cheaper method — and lost on C3 and C4). Mixed aggregate is 0.775, identical to Phase 2.
  • PASS: no. SHIP: no.

Honest read: the method is too conservative, NOT too coupled to the judge. The prompt-coupling risk this sub-step was guarding against did not materialise — but only because the method failed in the opposite direction (vacuous under-counting, the same failure mode that gave Phase 1 a row of fake "0.90 mean" winners).

Why Opus under-counted so hard

Reading the 240 per-window responses, three themes recur:

  1. 1-second windows are too short. The judge gets 3 seconds × 5 frames. We gave Opus 1 second × 6 frames. Bee transits across the band take ~0.3–1.0s on these clips, and at 6-frame stride the model often sees the bee on one side in frame N and lost in clutter in frame N+1, never on the other side. The model honoured its undercount instruction and returned 0.
  2. Per-bee tracking is hard at this density. On C3/C4 (21 and 40 bees/frame), the strip image is busy enough that "the same bee on opposite sides in two different cells" is genuinely difficult to identify without bbox/id help.
  3. The strict prompt only tightens the bar Opus was already exceeding. Standard prompt produced 0. Strict prompt can do no better.

Recommendations for iter 2 (handoff to orchestrator)

The orchestrator should pick ONE of these, not both — they're substitutable.

  1. Lengthen the Opus-window method to 3 seconds × 8 frames and rebalance the prompt to ask for in/out only (drop observed_crossings — the per-bee accounting was rejected by the model anyway). This trades the "different framing" honesty constraint for actually getting non-zero counts. The prompt coupling risk would reappear; would need a careful per-window comparison.
  2. Build a hybrid: MOG2 candidate events → Opus 1-second context verification with strict prompt. Use MOG2's events as proposals (where we know the bee showed up and which side it ended on), pass Opus a tighter ±0.5s window around each proposed event, and ask only "is this a real crossing in the proposed direction?" That's Phase 2's verifier with a different overlay — and Phase 2 showed that approach failed because the bbox was static, not because the prompt was wrong. Phase 3's planned fix (per-frame moving bbox) could unblock it.
  3. The cheap win: spend iter 2 on a per-camera MOG2 re-tune targeting C3 specifically. Phase 2's tuner used a coarse grid; a focused grid around var_threshold=28, min_hits=30, band_px=24 with finer steps and a longer warmup might recover a few of the 9 missed crossings. The 0.10-point gain from Phase 1→Phase 2 came from the same kind of work, and C3 alone is what's holding the aggregate under PASS.

I'd advise option 3 next — it's the cheapest and the failure mode is well understood. Option 2 is the most interesting but requires Phase 3 work first. Option 1 carries the highest prompt-coupling risk and Opus's track record this iter (refusing to count when not absolutely certain) suggests it would still under-count without a cleaner per-bee visual cue.
