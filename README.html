bee-counter

Counts honeybee entries into a hive from hive-entrance camera footage. Accuracy on the count is the only first-order metric — throughput and code minimalism are subordinate (CLAUDE.md, spec.md).

Scope

Entries only. Exits (bees emerging from the hive) are out of scope. The deliverable counts bees going in, reproducible from a saved config + the raw video. C1 is the fully-labelled headline camera; all four cameras now have manual GT and scored counts (see All cameras).

Headline result — C1

C1 has manual ground truth: 51 hand-labelled IN events (ground_truth_labels.jsonl). Two independent counters — one motion-based, one detector-based — both hit the count from completely different signals:

Counter Predicted IN Ratio vs 51 Temporal P / R / F1 (±15f) Signal
Motion "vanish-into-dark" (shipped) 52 1.02 0.75 / 0.76 / 0.76 MOG2 motion blobs
Absorption "detector terminations" 53 1.04 0.77 / 0.80 / 0.79 fine-tuned-YOLO chains dying in the dark zone

Both meet the count goal (within ±10%); absorption has the higher temporal F1 and recall. That two methods built on unrelated evidence (motion vs detection) agree on the count is itself a validation signal — see Cross-method validation. Temporal F1 plateaus ~0.76–0.79: at a crowded entrance "entered" is genuinely ambiguous and the GT is itself approximate (see decisions.md). Each counter runs in a few seconds on CPU over the 900-frame clip.

The original overnight exploration framed success as Claude-as-judge agreement and reported a "0.775 cap". That proxy badly undercounts entries (the judge said C1=0), so it was replaced by the manual GT above. The judge history is preserved in final.md below the rule as the honest record.

How the counter works

video → crop(ROI) → grayscale → CLAHE → motion → blobs → Hungarian tracker → entry counter → IN events

A bee enters by arriving at a dark entrance notch from any direction and disappearing into it. The counter (VanishEntryCounter) counts tracks that end inside the entrance zone having started outside it (direction-agnostic). Tracks born inside the zone are emerging bees (exits) and are excluded.

Counting methods

Method Detector Result on C1 Where
Motion (shipped) MOG2 background subtraction + connected-component blobs → Hungarian tracker → VanishEntryCounter 52/51, F1 0.76 — needs no weights scripts/run_c1_entry.py, configs/c1_entry.yaml
Absorption (best temporal) Fine-tuned YOLO11s → short greedy local tracks → count chains that terminate deep in the dark zone 53/51, F1 0.79 — highest recall scripts/count_c1_absorption.py, configs/c1_absorption.yaml
YOLO + global tracker (ruled out) Fine-tuned YOLO11s → ByteTrack/BoT-SORT → zone-entry rule recall up to 0.94 but track fragmentation overcounts (62) → F1 plateaus 0.65–0.73 scripts/count_c1_yolo.py, scripts/count_c1_tracks.py

The two shipped methods live in src/beecounter/count/{vanish_entry,absorption}.py. That package also holds ~9 Phase-1 / iteration experiments that were tried and dropped — src/beecounter/count/README.md is the module index that says which two ship and why the rest are kept only for the record. configs/README.md does the same for the 22 YAML configs (which 11 are on the shipped path, which are detector-experiment or Phase-1/2 leftovers).

The motion method's small blobs are load-bearing — the tiny last-motion sliver at the hole edge is the vanish signal, so raising min_area/closing harder collapses recall and the count. The fine-tuned detector gives one clean box per bee (recall ~0.94 on its own dataset). The absorption counter exploits that recall without needing a stable global identity: a bee that enters descends into a dark hole and its detection chain simply ends there, so counting local chain terminations deep in the zone sidesteps the fragmentation that defeats a global tracker (the third row above).

Cross-method validation

The motion and absorption counters share no code path — one is background-subtraction motion, the other fine-tuned detection — yet both land within ±10% of the 51 GT entries. Their intersection (entries both counters fire on within ±15 frames) is a high-confidence core of ~26 events at precision 0.90. Fusing them does not beat absorption alone: a bounded sweep of union / intersection / "absorption + motion-only" fusions (scripts/explore_c1_fusion.py) tops out at F1 0.75 — union re-counts the same bee twice, intersection drops half the real entries. The value of the second method is agreement as evidence, not a better count. Reproduce:

uv run --no-sync python scripts/explore_c1_fusion.py

Reproduce

Whole project, one command — regenerates each camera's (gitignored) detection cache if missing, then runs both counters on all 4 cameras and scores each in its GT window → scoreboard.md:

bash scripts/reproduce.sh

(Needs the source videos under data/raw/videos/ and the fine-tuned weights at results/runs/yolo_train/c1_finetune/weights/best.pt — both gitignored; missing rows are skipped with a note, never fabricated.)

Or run a single method and score it against ground truth in one shot:

# C1 — motion counter (ships), run + annotate + score vs the 51 manual GT labels
uv run python scripts/run_c1_entry.py --config configs/c1_entry.yaml --annotate --score

# C1 — absorption counter (best temporal F1), reads precomputed detections, no GPU
uv run python scripts/count_c1_absorption.py --config configs/c1_absorption.yaml --score

# Whole-project scoreboard — BOTH counters on all 4 cameras, scored in each GT window
uv run bee run                               # CLI entry point → scoreboard.md
uv run bee run --reproduce                   # regenerate detection caches first (== reproduce.sh)
uv run python scripts/scoreboard.py          # equivalent, direct script invocation

# C2/C3/C4 — absorption counter (the winner). Detections are gitignored; regenerate once:
uv run python scripts/detect_bees_c1.py --weights results/runs/yolo_train/c1_finetune/weights/best.pt \
    --camera C3 --conf 0.1 --preset bright --out results/runs/c3_yolo_detections_ft.json
uv run python scripts/count_c1_absorption.py --config configs/c3_absorption.yaml

# Detector path — YOLO detections → tracker → counter (re-applies conf without re-inferring)
uv run python scripts/count_c1_yolo.py --detections results/runs/c1_yolo_detections.json --conf 0.3

# Score any method's events.jsonl against GT (also appends a bakeoff row)
uv run python scripts/compare_to_gt.py --camera C1 --events <run_dir>/events.jsonl

# Debug viewer — entrance microscope, per-frame overlays, polygon/crop editor, GT labeler
uv run bee viewer            # http://127.0.0.1:8765   (microscope at /microscope/C1)

Every run writes results/runs/entry_<cam>_<ts>/ with events.jsonl, counts.json, config.yaml, and (with --annotate) annotated.mp4.

Full dataset (704 videos, the whole recording)

The 2026-04-30 Drive download (704 clips, 5.85 h) is processed end-to-end by four scripts; all are idempotent/resumable and emit null (never 0) on a per-clip failure. Source videos live under data/raw/incoming/ (gitignored); manifests, the timeline, the per-clip exports, plots, and reports are committed.

# 2. Detect (YOLO-FT on MPS) + absorption-count every clip (~16-30s/clip, serial on GPU)

The full-dataset method is the shipped absorption counter, unchanged — it reproduces the committed scoreboard exactly on all four manual-GT clips (dataset_report.md §Validation).

Per-camera config

run_c1_entry.py is camera-generic — point --config at a per-camera YAML. Each config sets the ROI (from the viewer crop in configs/microscope.yaml), the entry geometry (auto dark-mask for C1's notches, or use_drawn_zones: true to read the hand-drawn polygon in configs/entry_zones.yaml), and the motion/tracker/dedup params.

All four cameras have committed manual GT (C1 fully labelled; C2/C3/C4 labelled up to a cut-off frame, so each is scored only inside its own window with compare_to_gt.py --camera <C> --max-frame <max GT frame>). Both counters run on every camera, and the absorption counter wins on all four. The table below is generated by scripts/scoreboard.py (windowed, ±15-frame temporal match):

Camera GT (window ≤f) Motion vanish Absorption (FT-det) Band (absorption)
C1 51 (→880, full) 52, r1.02, F1 0.76 52, r1.02, F1 0.78 ±10%
C2 74 (→544) 42, r0.57, F1 0.69 73, r0.99, F1 0.79 ±10%
C3 48 (→649) 22, r0.46, F1 0.43 49, r1.02, F1 0.72 ±10%
C4 42 (→166) 7, r0.17, F1 0.29 38, r0.90, F1 0.93 ±10%

The motion counter under-counts C2–C4, but this is not structural. Motion needs a bee to descend into a visible dark hole (the vanish signal), which the dense/crowded/grassy entrances of C2–C4 hide, so its recall collapses (C1 0.76 → C4 0.17). The absorption counter only needs the detector to see the bee and its local detection chain to terminate inside the entry zone — so the C1-fine-tuned YOLO detector, applied as-is to the other crops (transfer, no per-camera fine-tune or box labels), lifts all four cameras into the ±10% count band. The bottleneck was the motion signal, not the cameras.

Two kinds of lever generalise the absorption counter per camera, both interpretable and density-driven — no per-camera fine-tune or box labels needed. (1) The gating params (detector floor min_conf, deep_frac, min_len, dedup_frames): C2 needed its gating loosened from C1's defaults — the user-drawn polygons hug the entrance, so C1's depth filter discarded real near-lip absorptions (precision stays ~1.0, so the recovered events are true entries). (2) The local-tracker association radius gate_px: C4 — the densest, grassiest crowd — needed it tightened 70→50, because in a dense crowd a loose gate lets a terminating chain be "stolen" by a neighbour and so suppresses recall. That single density-dependent lever took C4 from 30/42 (r0.71, OUT) to 38/42 (r0.90, F1 0.93, IN band), overturning the earlier "C4 is detection-limited, needs fine-tune" verdict. Per-camera configs: configs/c{1,2,3,4}_absorption.yaml. See decisions.md for the full per-camera recall analysis and robustness.md for the plateau-vs-overfit check on all four.
